# GLOBAL DATA STORAGE, IN-MEMORY & PERSISTENCE ARCHITECTURE RULES (2026 STANDARDS)

## 1. DATA PERSISTENCE DUALITY PRINCIPLE (MEMORY VS DISK)
Systems MUST strictly categorize all application data into two operational tiers:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                      APPLICATION DATA ARCHITECTURE                     │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
          ┌─────────────────────────┴─────────────────────────┐
          ▼                                                   ▼
┌───────────────────────────────────┐               ┌───────────────────────────────────┐
│     TIER 1: IN-MEMORY (RAM)       │               │    TIER 2: PERSISTENT DISK        │
│   (Redis / Valkey / Memcached)    │               │  (PostgreSQL 16/17+, MySQL 8.4+)  │
├───────────────────────────────────┤               ├───────────────────────────────────┤
│ • Session State & Tokens          │               │ • Transactional Business Data     │
│ • High-Frequency Cache            │               │ • User Profiles & Auth Credentials│
│ • Rate Limit Counters             │               │ • Audit Logs & Financial Records  │
│ • Temporary Queue Payload         │               │ • System Core Entities            │
│ • Volatile Real-Time Metrics      │               │ • Historical Immutable Records    │
└───────────────────────────────────┘               └───────────────────────────────────┘
Rule of Durability: IF data loss causes financial discrepancy, legal/compliance failure, or permanent loss of user identity, it MUST be committed to Tier 2 (Persistent Disk) within a single ACID transaction block before returning success to the client.Rule of Ephemerality: Cache (Tier 1) MUST always be treatable as disposable. The application MUST be capable of rebuilding its entire in-memory cache state directly from the persistent database without application downtime.2. IN-MEMORY & RAM STORAGE STANDARDS (REDIS / VALKEY)A. TTL (Time-To-Live) & OOM Prevention PolicyMandatory TTL: EVERY cache key created in Redis/Valkey MUST explicitly set an expiration time (EXPIRE / SETEX). Unbounded/immortal keys are STRICTLY FORBIDDEN (prevents Out-Of-Memory / OOM crashes).Jitter Strategy for TTL: Add randomized jitter (+/- 10% to 15% variation) to TTL values on bulk cached keys to prevent Cache Stampede (Thundering Herd Problem) where thousands of cache keys expire simultaneously.B. Caching Pattern ArchitectureCache-Aside (Lazy Loading): Preferred default for read-heavy entities.Read from Tier 1 (RAM).On Cache Miss: Read from Tier 2 (Database) -> Write to Tier 1 -> Return payload.Write-Through / Write-Behind: Used ONLY for high-throughput batch write counters (e.g., page view tracking) before flushing to primary database in background workers.C. Data Structure Selection MatrixData TypeRedis Data StructurePrimary Use CaseSimple StringsStringHTML fragments, JSON stringified payloads, session tokens.Object EntitiesHashUser session attributes, granular fields modification without re-serializing.Unique CollectionsSetOnline user IDs list, unique IP address tracking.Leaderboards / RankSorted Set (ZSET)Rate limiting sliding windows, ordered queue priorities.Message StreamingStream / PubSubEvent-driven job processing and real-time broadcasts.3. RELATIONAL PERSISTENT STORAGE STANDARDS (POSTGRESQL & MYSQL)A. Database Engine & EncodingPostgreSQL: Version 16+ or 17+. Encoding MUST be UTF8 with LC_COLLATE = 'en_US.UTF-8' or C.UTF-8.MySQL / MariaDB: MySQL 8.4 LTS+ or MariaDB 11.4 LTS+. Engine MUST be InnoDB. Default Character Set MUST be utf8mb4 with collation utf8mb4_unicode_ci or utf8mb4_0900_ai_ci.B. Primary Key & Identifier Strategy (UUID v7 vs Auto-Increment)High-Concurrency Distributed Systems: MUST use UUID v7 (time-ordered 128-bit integer).Why: UUID v7 combines Unix timestamp with randomness, preventing B-Tree index page fragmentation while avoiding sequential ID enumeration attacks.Internal / Single-Node CRUD Systems: BIGINT UNSIGNED AUTO_INCREMENT (MySQL) or BIGSERIAL / GENERATED ALWAYS AS IDENTITY (PostgreSQL) is acceptable.STRICT PROHIBITION: NEVER use random UUID v4 as a primary clustered index key. Random UUID v4 causes severe write performance degradation due to continuous B-Tree index rebalancing.C. Transaction Isolation LevelsDefault Isolation Level:PostgreSQL: READ COMMITTED (Prevents Dirty Reads).MySQL: REPEATABLE READ (Prevents Dirty Reads and Non-Repeatable Reads).Financial & Double-Entry Ledger Transactions: MUST explicitly execute under SERIALIZABLE isolation OR utilize SELECT FOR UPDATE (Pessimistic Locking) with strict row-level lock boundaries.4. DATA SECURITY, PRIVACY & ENCRYPTION AT RESTPII (Personally Identifiable Information) Encryption:Sensitive columns (e.g., National ID / NIK, Credit Card Numbers, Health Data) MUST be encrypted before persistence using AES-256-GCM or Sodium/SecretBox.NEVER store plain-text secrets, passwords, or API tokens in database tables. Passwords MUST be hashed using argon2id or bcrypt (cost factor $\ge 12$).Soft Deletes vs Hard Deletes:Financial, Audit, and Transactional logs MUST NEVER be hard-deleted from tables (is_deleted or deleted_at timestamp flag required).PII records subject to privacy regulation (GDPR / UU PDP) MUST support anonymization scripts (overwriting user identity with hash signatures upon deletion request).5. INDEXING, CONCURRENCY CONTROL & PERFORMANCEA. Indexing Hierarchy RulesHigh-Cardinality Columns First: Composite indexes MUST place columns with highest selectivity/cardinality first: INDEX idx_user_status (tenant_id, status, created_at).Covering Indexes: For high-frequency query endpoints, include target select columns in index definition to achieve Index-Only Scans.Index Count Guardrail: Do NOT create more than 5-7 indexes per table without performance benchmark justification (excessive indexes degrade INSERT, UPDATE, and DELETE performance).B. Concurrency Control MechanismsOptimistic Locking: Preferred for web UI forms where conflicts are rare. Use an integer version column:SQLUPDATE accounts
SET balance = balance - 100, version = version + 1
WHERE id = 42 AND version = 5;
Pessimistic Locking: Required for inventory stock reservation and flash-sale allocations:SQLSELECT * FROM inventory WHERE product_id = 100 FOR UPDATE;
