## 1. HARDWARE & RUNTIME RESOURCE MANAGEMENT ARCHITECTURE
All backend systems, runtime engines (Node.js, Go, PHP-FPM/Swoole, Java/Kotlin, Python), and container environments MUST operate under strict hardware budget limits to guarantee system stability and prevent unpredictable Resource Starvation.

2. MEMORY MANAGEMENT & GARBAGE COLLECTION (GC) RULESA. Stack vs Heap Allocation EfficiencyStack First Allocation: Prefer allocation on the Stack over the Heap for short-lived, fixed-size data structures. Stack allocation incurs zero GC overhead.Escape Analysis: Avoid returning pointers or references to local scope variables in compiled runtimes (Go/Rust/C++) unless necessary, as this forces memory to "escape" to the Heap.B. Garbage Collection (GC) Tuning & ControlGC Pause Threshold Limit: Total GC pause duration MUST NOT exceed 2% of cumulative execution runtime or cause latency spikes higher than 10ms (p99).Runtime-Specific GC Guidelines:Node.js (V8): Explicitly set memory limits in containerized environments via --max-old-space-size=<MB> (e.g., set to 75-80% of total container RAM).Go: Adjust GOGC (default 100) or GOMEMLIMIT to prevent aggressive GC triggering before reaching target container memory boundaries.Java / JVM: Use low-latency concurrent collectors like ZGC or Shenandoah for workloads requiring ultra-low latency (-XX:+UseZGC).PHP (Long-running Swoole/RoadRunner): Manually trigger cycle collection (gc_collect_cycles()) or recycle worker processes after serving $N$ requests to prevent slow memory leaks.C. Zero Memory Leak DirectivesResource Deallocation: ALL open file descriptors, database connections, sockets, and stream handles MUST be closed explicitly using deterministic cleanup patterns (using, try-finally, or defer).Dangling Listeners & Closures: Unsubscribe from event listeners, RxJS streams, and static singleton event buses when UI components or worker contexts are destroyed.3. THREAD & CONCURRENCY MANAGEMENTA. Workload Isolation: I/O Bound vs CPU BoundI/O-Bound Workloads: MUST utilize Non-Blocking Asynchronous I/O (Event Loop / Async-Await / Goroutines / Fibers). NEVER block OS threads on I/O operations (network, disk, DB queries).CPU-Bound Workloads: Heavy computations (image processing, encryption, PDF generation) MUST be offloaded to dedicated Worker Pools / Background Jobs. NEVER run CPU-intensive blocking loops inside the main Event Loop thread.B. Thread Pool Sizing FormulaThread pool capacities MUST NOT be arbitrary. Calculate maximum worker pool size using the standard concurrency formula:$$\text{Thread Pool Size} = \text{CPU Cores} \times \left(1 + \frac{\text{Wait Time}}{\text{Service Time}}\right)$$For CPU-bound tasks: Set workers equal to $\text{CPU Cores} + 1$.For I/O-bound tasks: Adjust ratio based on network/disk wait times, constrained by maximum database pool limits.C. Concurrency Safety & Lock MinimizationPrevent Deadlocks: Acquire locks in a strict, uniform global order across all service modules. Always set a lock timeout (TryLock with TTL).Lock Granularity: Prefer fine-grained locks or lock-free atomic operations (AtomicInteger, CAS - Compare And Swap) over coarse-grained global mutex locks.4. CPU OPTIMIZATION & PROCESS BOUNDARIESProcess Worker Allocation Rule:For multi-process process managers (e.g., PHP-FPM, Gunicorn, PM2 Cluster), calculate max workers based on available RAM:$$\text{Max Workers} = \frac{\text{Total Server RAM} - \text{OS Base Memory}}{\text{Average RAM Usage per Process}}$$Prevent Context Switching: Avoid spawning more OS threads than available physical CPU cores for compute tasks to minimize CPU context switching overhead.CPU Affinity & Throttling: In Kubernetes environments, configure CPU requests equal to CPU limits for Guaranteed Quality of Service (QoS), preventing performance degradation from CPU throttling.5. GPU ACCELERATION & COMPUTE OFF-LOADINGOffloading Criteria: Utilize GPU acceleration (CUDA, OpenCL, WebGPU) ONLY for massively parallel matrix operations, deep learning inference, image/video encoding, or large dataset vector indexing.PCIe Bottleneck Mitigation: Host-to-Device (CPU to GPU) data transfer over PCIe is slow. Group data into Bulk Batches before sending to GPU memory (VRAM) rather than transferring individual records one by one.VRAM Memory Allocation: Allocate and reuse persistent GPU VRAM memory buffers. Avoid allocating and freeing GPU memory dynamically inside hot loops.6. Hardware & Data Locality Alignment (L1/L2/L3 Cache)Write Cache-Friendly Data Structures: Prefer contiguous memory layouts (Arrays) over deeply nested pointer graph objects to leverage CPU L1/L2 cache prefetching (Sequential Memory Access).B. Software Caching PoliciesEviction Strategy: Default to LRU (Least Recently Used) or LFU (Least Frequently Used) eviction policies.Cache Invalidation Discipline: Invalidate cache explicitly upon entity mutation (UPDATE / DELETE). Never rely solely on long TTLs for volatile state data.Protection Against Cache Anomalies:Cache Penetration: Store null flags or Bloom Filters for non-existent keys to prevent queries from reaching the database.Cache Breakdown: Use Mutex / SingleFlight to allow only one process to query the DB and rebuild cache on key expiration.7.
